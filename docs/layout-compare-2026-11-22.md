# 葉方式と per-vertex 方式の比較（シミュレーション）

2026-11-22。slab の空間を「k 頂点の葉でまとめて管理する方式」と「頂点ごとに別々の span で管理する方式」を、それぞれの最善形で比べた。結論は次のとおり。

- **更新は per-vertex が優れる。** 挿入1回あたりの移動量は 1/5〜1/15 で、最悪ケースの移動量は 1023 slot で上限が付く。
- **メモリ使用量は、アロケータの tag（span ごとに32B）を含めると per-vertex の方が多い**（Orkut で 1.70〜1.78 倍に対して葉方式 1.61〜1.64 倍）。最初の版の表は slab だけを数えていて、per-vertex の方が少ないと誤って結論していた（下の「訂正」）。
- **頂点 id 順の scan は葉方式が優れる。** 隙間を読み飛ばしてまとめる場合、読み出し回数は葉方式の方が 4〜30 倍少ない。
- **アロケータの呼び出しは per-vertex が多い**（葉方式の最善形の 4〜14 倍）。
- 葉の中の rebalance の方針は、局所シフトと比例 rebalance の安い方をその都度選ぶ「適応型」が最善だった。ただし局所シフトだけの場合との差は数%で、比例 rebalance だけにすると移動量が 1.4〜3.8 倍に増える。
- どちらが総合的に速いかは、IC 上での「読み出し1回の固定費」「アロケータ呼び出し1回のコスト」と、Gleaph のアクセスの比率で決まる。このシミュレーションでは決められない。

## 方法

シミュレータは [`crates/benches/examples/layout_compare.rs`](../crates/benches/examples/layout_compare.rs)。slab の span は `lara-core` の実際のアロケータ（外部 boundary tag と TLSF の2段索引、その場での拡張 `try_extend` を含む）から取る。両方式に共通の前提は次のとおり。

- 辺は 1 slot。4本以下の行は descriptor の中に置く（tiny、ADR 0096 の 16 バイト payload に相当）。
- 1024 本に達した行は tree に移す（slab の外。両方式で同じ扱いなので、scan の比較からは除く）。
- 挿入のみ。有向辺をストリームの順に入れる。ラベルなし。

各方式の最善形は次のとおり。

| 方式 | 動作 |
|---|---|
| 葉 | 葉が初めて slab を必要としたとき、全行を `alloc_for(x) = max(x, min(2x, 1024))` の容量で詰める。行が溢れたら、まず span の中で下記の方針のどれかで処理する。span の中で処理できない（葉全体の余白が足りない）ときだけ、その場での拡張と詰め直しを試し、だめなら新しい span に relocation する。 |
| 葉の方針: shift | 一番近くで余白を持つ行から余白の半分を借り、間の行だけをずらす。 |
| 葉の方針: weighted | span の中で全行を並べ直し、葉の余白を各行の目標 headroom `alloc_for(x) - x` に比例して配る（PMA の in-window rebalance に当たる）。 |
| 葉の方針: adaptive | その挿入で移動量が少ない方（shift か weighted）を選ぶ。同じなら weighted。 |
| per-vertex（best） | 行ごとに、8 から始めて係数 g で増えるクラス（上限 1024）の span を持つ。溢れたら、その場での拡張を試し、だめなら次のクラスへ relocation する。 |
| 葉（repack only） | 校正用。行が溢れるたびに葉全体を新しい span に詰め直す。旧 `lara-graph` の log 無効時の `rebalance_leaf` と同じ挙動。 |

計測項目は次のとおり。

- 移動量：既存の辺をコピーした slot 数。新しく書く辺は含めない。
- アロケータ呼び出し：確保、解放、その場での拡張の合計。
- メモリ量：アロケータの frontier ÷ slab にある生存辺。
- scan：頂点 id 順に全行を読む。次の行が直前の読み出しの終端から gap slot 以内で始まれば、同じ1回の読み出しにまとめる（間の隙間も読む）。読み出し量は slab の生存辺との比で示す。

## 校正

葉（repack only）を、同じストリームに対する旧 `lara-graph`（segment=31、log 無効、tree 昇格 1024、free span 有効）の実測と比べた（[`layout_calibrate.rs`](../crates/benches/examples/layout_calibrate.rs)）。

| ワークロード | relocation（モデル） | rebalance（実装） | メモリ量（モデル） | メモリ量（実装） |
|---|---:|---:|---:|---:|
| 一様 1M 頂点 / 1000万辺 | 336,533 | 306,398 | 2.06 | 2.05 |

回数は約1割の差、メモリ量はほぼ一致した。冪乗則のワークロードは実装側の分母に tree の辺が入るため、メモリ量を直接は比べられない。最初の版のモデルには、実装にない「葉の中だけで済む安い rebalance」が入っていて、回数が実装の約3倍になった。実装を読み直して原因（tiny 行を relocation のときに slab へ移す）を特定し、修正した。

## 葉の中の rebalance の方針

3つの方針で、relocation、その場での拡張、アロケータ呼び出し、メモリ量はまったく同じだった。span の外に出るのは葉全体の余白が尽きたときだけで、それは span の中の方針に依存しないためである。違いは移動量だけに出る。

| ワークロード | k | shift | weighted | adaptive |
|---|---:|---:|---:|---:|
| Orkut | 16 | 10.31 | 14.87 | 9.81 |
| Orkut | 31 | 13.63 | 21.32 | 12.81 |
| 冪乗則 | 16 | 5.21 | 7.40 | 5.36 |
| 冪乗則 | 31 | 9.34 | 13.91 | 9.36 |
| 一様 | 16 | 4.70 | 12.15 | 4.74 |
| 一様 | 31 | 6.15 | 23.38 | 6.18 |

（値は挿入1回あたりの移動量）

- **weighted は移動量が多い。** 余白を比例配分すると次に溢れるまでの間隔が延びるので、回数は Orkut と冪乗則で shift の 0.6〜0.9 倍に減る（一様分布ではほぼ同じ）。ただし1回ごとに葉全体を並べ直すので、合計では 1.4〜3.8 倍に増える。償却の効果より、1回あたりのコストの方が大きい。
- **adaptive は Orkut で shift より 5〜6% 少ない。** 合成ワークロードでは、その時点で安い方を選ぶことが後の挿入で裏目に出る場合があり、shift よりわずかに多い（最大約 3%）。
- 以下では、葉方式の最善形を adaptive とする。shift と比べても数%の差しかないので、結論はどちらで比べても変わらない。

## 読み取れること

1. **移動量は per-vertex が 1/5〜1/15。** 葉方式は、span の中で処理するたびに、複数の行をずらす。Orkut では1回の挿入につき平均 0.3〜0.4 回、この処理が起きる。per-vertex は、自分の行を次のクラスに移すときにしか動かない。
2. **最悪ケースは per-vertex だけに明確な上限がある。** per-vertex の最大移動量は構造上 1023（tree 閾値の手前）。葉方式は、葉の中の行をまとめて動かすため、3,000〜27,000 に達する。「更新の計算量を有界にする」という LARA の目標には、per-vertex の方がはっきり合う。
3. **slab だけを見れば per-vertex が少ないが、tag を含めると逆転する。** slab だけなら g=1.5 で 1.25 倍、g=2 で 1.41 倍、葉方式は 1.51〜1.64 倍だった。下の「訂正」を参照。
4. **アロケータの呼び出しは per-vertex が多い。** Orkut で葉方式の 4〜8 倍、一様分布では 8〜14 倍。前回の per-vertex 試作で「relocation の頻度が増えて不利になった」のは、この点と一致する。ただし、移動するデータ量そのものは per-vertex の方がはるかに少ない。
5. **その場での拡張は、per-vertex ではほとんど効かない。** 行ごとの span が交互に確保されるため、直後が空いていることが少ない（g=1.5 で relocation の約4%）。
6. **頂点 id 順の scan は葉方式が強い。** 隙間を読まない（gap 0）なら回数はほぼ同じ。256 slot までの隙間を読み飛ばしてまとめると、葉方式は回数が 1/4〜1/30 になり、代わりに読み出し量が 1.4 倍程度に増える。per-vertex は行が散らばるので、まとめられない。1頂点だけを読む traversal では、両方式とも1回の連続読み出しで、差は出ない。

## 訂正：アロケータの tag を含めたメモリ使用量

上の表の「メモリ量」は slab の frontier だけを数えていて、span アロケータの tag（span 1つにつき32B、slab とは別のメモリ）を含めていなかった。per-vertex は小さい run が多いので、tag の数が葉方式よりずっと多い。tag を含めて測り直した結果は次のとおり（(frontier × 4B + tag のバイト数) ÷ (生存辺 × 4B)）。

| ワークロード | 葉 k=16 | 葉 k=31 | per-vertex g=2 | per-vertex g=1.5 |
|---|---:|---:|---:|---:|
| Orkut | 1.61 | 1.64 | 1.78 | 1.70 |
| 冪乗則 | 1.66 | 1.64 | 1.76 | 1.68 |
| 一様 | 1.71 | 1.63 | 2.30 | 2.18 |

tag の数は、作られたレコードの総数（再利用待ちを含む）で数えた。メモリは確保すると縮まないので、これが実際に使う量になる。per-vertex を採る理由は移動量と最悪ケースの上限であり、メモリ量ではない。小さい run のメタデータを減らす設計が必要になる。

## 判断に足りないもの

- **IC 上のコスト。** 「読み出し1回の固定費」と「アロケータ呼び出し1回のコスト」（tag レコード数件の読み書き）の命令数がわからないと、4 と 6 の重みが決まらない。次の段階で、両方式の最小限の永続版を作り、canbench で命令数を測る必要がある。
- **Gleaph のアクセスの比率。** id 順の一括 scan が多いなら葉方式、頂点単位の traversal と更新が中心なら per-vertex が有利になる。
- **モデルの範囲。** 削除、ラベル（バケットごとの領域）、spill、葉方式で行をずらすときの descriptor の書き換えコスト（ずらした行の数だけ base を書き直す）は入っていない。最後の項目は葉方式に不利に働く。
- **per-vertex の局所性の回復策**（頂点 id の範囲ごとに確保元を寄せる、id 順に並べ直す段階的な compaction）は試していない。
