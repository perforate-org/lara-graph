# per-bucket ストレージの3案比較（メタデータを含めたシミュレーション）

2026-11-22。小さい run をチャンクにまとめる前提で、次の3案を、アロケータのメタデータを含めて比べた。

- **A：TLSF とチャンク**：8〜128 slot の run は、TLSF から取った 1024 slot のチャンクを区切って使う。256 slot 以上の run とページは TLSF から直接取り、その場での拡張も試す。
- **B：統一ページストア**：すべてを 1024 slot のページの固定長プールから取る。1024 slot 未満の run は、ページを区切ったチャンクに入れる。
- **C：葉方式**（参考）：既存の比較シミュレータの adaptive（k=16、31）。

結論は次のとおり。

- **B は A と同等以上だった。** メモリ使用量は約 0.7% 少なく、メモリの読み書き回数は 3〜20% 少なく、移動量は同じだった。A のその場での拡張は、移動量をまったく減らさなかった。
- **チャンクにまとめると、メモリ使用量でも葉方式に勝つ。** descriptor を除いた比較で、B は葉方式より 10〜19% 少ない。移動量は、従来どおり葉方式の 1/5〜1/15 である。
- **疎なグラフでは、頂点ごとの descriptor がメモリの大半を占める。** Orkut のサブセットでは、descriptor（24B/頂点）だけで辺のデータの 1.84 倍になる。inline の容量を5本から7本（descriptor 32B）に増やすと、Orkut と冪乗則では全体の使用量がかえって増えた。
- 以上から、**統一ページストア（B）を採り、inline は5本（descriptor 24B）のままにする。** descriptor を小さくする工夫は、次の改善候補になる。

## 方法

シミュレータは [`storage_compare.rs`](../crates/benches/examples/storage_compare.rs)（A と B）と [`layout_compare.rs`](../crates/benches/examples/layout_compare.rs)（C）。

- バケットは A と B で共通である。inline に T 本（T=5 で descriptor 24B、T=7 で 32B）、run は 8〜1024 slot の2のべき乗、1024 本を超えたら Paged。満杯の run とページの間は、どちらの方向もコピーなしで移る。
- Paged の索引は、1ページに収まるうちは1段、超えたら2段にする（1回のコピー量に上限を付けるため）。索引のエントリは A が 14B、B が 6B。
- メタデータは次のとおり数えた。
  - A：TLSF の tag（実測。span ごとに32B）と、チャンクごとの記録 32B（ピーク時の数）。
  - B：ページごとのディレクトリ 32B（作ったページの総数）。
  - C：TLSF の tag（実測）と、tree に移った辺の容量（1024 本ごとに 4096B）。
- メモリの読み書き回数は、TLSF の分が実測、チャンクとプールの分が推定値である（チャンクの slot の取得・返却は読み1回と書き1回、ページの取得は読み2回と書き2回、返却は読み1回と書き2回）。
- 分母は、総辺数×4B とした。

## 結果：葉方式（C）との比較

葉方式のモデルは頂点ごとの行（descriptor に当たるもの）を数えていないので、descriptor を除いた値で比べる。inline の容量は、葉方式が4本、A と B が5本で、ほぼ同じ条件である。

| ワークロード | 葉 k=16 | 葉 k=31 | A（T=5） | B（T=5） | 移動 slot / 挿入（葉 k=16 / B） |
|---|---:|---:|---:|---:|---|
| Orkut | 1.585 | 1.620 | 1.294 | 1.283 | 9.81 / 1.14 |
| 冪乗則 | 1.268 | 1.280 | 1.078 | 1.071 | 5.36 / 0.56 |
| 一様 | 1.710 | 1.627 | 1.478 | 1.466 | 4.74 / 1.04 |

参考までに、チャンクを使わない per-vertex（TLSF だけ、g=2）は、Orkut で 1.647、一様で 2.275 だった。チャンクにまとめる効果は、Orkut で約 22% にあたる。

## 読み取れること

1. **B は A に、どの指標でも劣らない。** メモリ使用量は 0.7〜0.9% 少ない。読み書き回数は 3〜20% 少なく、ページが多いワークロードほど差が大きい。移動量はまったく同じで、A のその場での拡張は効いていない。B には可変長のアロケータ（TLSF と boundary tag）が要らないので、構成も単純になる。
2. **チャンクで小さい run のメタデータを減らすと、メモリ使用量でも葉方式に勝つ。** descriptor を除いて、B は葉方式より 10〜19% 少ない。前回は tag を含めると per-vertex が負けていたが、その原因は小さい run ごとの tag だった。
3. **inline の容量を増やすのは逆効果だった。** descriptor を含めると、Orkut と冪乗則では T=7 の方が全体の使用量が多い（Orkut で 3.13 に対して 3.69）。一様分布だけ、わずかに少ない（2.07 に対して 2.03）。
4. **疎なグラフでは、descriptor のサイズが最大の要因である。** Orkut のサブセット（平均次数 約3.3）では、descriptor だけで辺のデータの 1.84 倍になる。ここを小さくする工夫（descriptor の縮小、辺のない頂点の扱いなど）は、チャンク化よりも大きく効く可能性がある。

## 追記：descriptor を 16B（inline 3本）にした場合

統一ページストアでは、Run の descriptor は約12B（kind、クラス、page_id、ページ内の位置、stored、live）、Paged は約16B で足りるので、descriptor 全体を 16B にできる。その場合、inline の余地は 14B で3本になる。B について3通りを比べた（descriptor を含めたメモリ使用量 ÷ 総辺数×4B）。

| ワークロード | 16B（3本） | 24B（5本） | 32B（7本） | 読み書き回数 / 操作（16B / 24B） |
|---|---:|---:|---:|---|
| Orkut | **2.590** | 3.127 | 3.686 | 0.316 / 0.296 |
| 冪乗則 | **1.544** | 1.671 | 1.839 | 0.119 / 0.101 |
| 冪乗則チャーン | **1.654** | 1.710 | 1.838 | 0.106 / 0.088 |
| 一様 | 2.083 | 2.066 | **2.033** | 0.482 / 0.470 |

16B にすると、Orkut で 17%、冪乗則で 8%、チャーンで 3% 減る。一様分布（どの頂点も次数 約10）だけは、わずかに増える（+0.8%）。代わりに、inline に収まらない頂点が増えて run が多くなるので、読み書き回数は 3〜20% 増える。疎なグラフでは descriptor の大きさが支配的なので、**descriptor は 16B（inline 3本）を採る**。

## 限界

- チャンクとプールの読み書き回数は推定値で、IC 上の命令数ではない。
- チャンクとディレクトリの記録の大きさ（32B）は、設計上の見積もりである。
- 削除後の run の縮小はモデルに入れていない。チャーンでの使用量は、縮小を入れれば下がる。
- 葉方式のモデルは、頂点ごとの行と葉ごとのメタデータ（PMA の木、カウント）を数えていない。
