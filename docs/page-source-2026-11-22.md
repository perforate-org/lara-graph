# 高次数バケットのページをどこから取るか（シミュレーション）

2026-11-22。1024 本を超えたバケットのページ（1024 slot）を、run と同じ span アロケータから取る方式（shared）と、専用の固定長プールから取る方式（pool）を比べた。pool は ic-stable-lara の LTB ストアと同じく固定長プールからページを取るが、tombstone の数をブロックのヘッダではなく索引の側に置く変種である。そのため索引のエントリは、LTB の root 配列の 4B ではなく 6B になる。

結論は次のとおり。

- **挿入だけなら、ほぼ差はない。** メモリ使用量は同じで、stable memory の読み書き回数の差は 1% 未満だった。
- **ハブが大きく縮むと、shared の方がメモリ使用量が 17% 少ない**（使用量 ÷ 格納した辺の数が、1.359 に対して 1.644）。pool では、空いたページの領域を run が使えないためである。
- **pool の利点は小さい。** 縮むワークロードで読み書き回数が 2.6% 少なく、索引のエントリが小さい（14B に対して 6B。scan で読む部分は 10B に対して 6B）程度だった。エントリは1ページ（4096B）に1つなので、容量の差は 0.2 ポイント、scan で読む量の差は 0.1 ポイントにとどまる。代わりに、昇格と降格でコピーが発生し、移動量は 1〜19% 増える。
- 以上から、**ページは shared（汎用の span アロケータ）から取る**ことにする。

## 方法

シミュレータは [`crates/benches/examples/page_source_compare.rs`](../crates/benches/examples/page_source_compare.rs)。バケットの挙動は lara-core に合わせた（Tiny は5本まで、run は 8〜1024 slot の2のべき乗で、その場での拡張を試してから relocation、1024 本を超えたら Paged）。span アロケータは lara-core の実物を使い、メモリの読み書き回数を数えた。

| 方式 | ページの取り方 | 昇格・降格 | 索引のエントリ |
|---|---|---|---|
| shared | run と同じ span アロケータ | コピーなし（満杯の run をそのままページ0にする。逆も同じ） | 開始 slot、tombstone の数、tag の ID（14B） |
| pool | 別メモリの固定長プール（空きリスト1本） | 昇格は run をページへ、降格はページを run へコピーする | ページ ID、tombstone の数（6B） |

pool の操作回数は推定値である。1回の取得を読み2回と書き2回（空きリストの先頭、リンク、先頭、ヘッダ）、1回の返却を読み1回と書き2回とした。

ワークロードは次の3つ。

1. **一様分布**（100万頂点、1000万辺）：ページがほとんど作られない対照。
2. **冪乗則**（beta=1.0、100万頂点、1000万辺）と **Orkut**（1000万辺サブセット）：挿入のみ。
3. **冪乗則のチャーン**：冪乗則で1000万辺を挿入する。次に、1024 本を超えた全バケットの辺の 90% を削除する。最後に、ハブが別の頂点になるよう順位をずらした冪乗則で、500万辺を挿入する。

|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 一様 | shared | 1.412 | 20,053,114 | 12,676,280 | 0 | 3.273 | 1.021 | 0 | 0 |
| 一様 | pool | 1.412 | 20,053,114 | 12,676,280 | 0 | 3.273 | 1.021 | 0 | 0 |
| 冪乗則 | shared | 1.223 | 4,629,675 | 3,198,676 | 0 | 0.783 | 0.558 | 681 | 0 |
| 冪乗則 | pool | 1.222 | 4,640,745 | 3,229,241 | 20,844 | 0.789 | 0.627 | 681 | 0 |
| 冪乗則チャーン | shared | **1.359** | 8,040,041 | 5,618,655 | 0 | 0.703 | 0.455 | 1,020 | 614 |
| 冪乗則チャーン | pool | **1.644** | 7,838,902 | 5,437,974 | 44,879 | 0.685 | 0.540 | 1,020 | 614 |
| Orkut | shared | 1.404 | 12,938,600 | 8,735,602 | 0 | 2.167 | 1.142 | 109 | 0 |

いずれのワークロードでも、ピーク時の使用量は最終時点と同じだった（最後まで増え続けるワークロードのため）。

## 読み取れること

1. **挿入だけでは、ページの取り方はほとんど効かない。** ページになるバケットは少数で（冪乗則で681個、Orkut で109個）、メモリ使用量はまったく同じだった。読み書き回数の差は 0.1〜0.8% だった。
2. **縮むと pool は領域を取り残す。** チャーンでは、削除で空いたページが pool に残り、後半の挿入（別の頂点の run）では使えない。shared では、空いたページが隣の空きと coalesce して、run の確保に再利用される。IC の stable memory は確保すると縮まないので、この差はそのまま費用の差になる。
3. **pool の速さの利点は小さい。** チャーンで読み書き回数が 2.6% 少なかった。ページの確保と解放が TLSF の検索より軽いためである。挿入のみでは、昇格時のコピーの分だけ、むしろわずかに多い。
4. **移動量は shared の方が少ない。** pool は昇格と降格のたびに 1024 slot をコピーする（冪乗則で +12%、チャーンで +19%）。

## 限界

- **IC 上の命令数ではない。** 数えたのはメモリの読み書きの回数で、pool の分は推定値である。
- **チャーンは極端な設定である。** 1024 本を超えたすべてのバケットから 90% を削除している。実際の Gleaph でハブがどの程度縮むかで、2の差の大きさは変わる。
- 削除は、最後の辺で穴を埋める今の方式で数えた。tombstone と compaction の方式でも、ページが空く時点は同じなので、比較の結論は変わらないと考えている。
